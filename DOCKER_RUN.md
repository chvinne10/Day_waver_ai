# Run Dayweave AI with Docker Desktop (Windows)

These steps run the Dayweave frontend, API, and PostgreSQL in Docker Compose. Compose is limited to the `dayweave-ai` project. PostgreSQL and uploaded-file data are kept in project named volumes when you stop or rebuild the app.

## Start the app

1. Install and start Docker Desktop. Wait until it says the engine is running.
2. Open PowerShell in this project folder and make the local environment file:

   ```powershell
   Copy-Item .env.example .env
   notepad .env
   ```

3. In `.env`, replace `POSTGRES_PASSWORD` with a strong local password. To save cloud AI keys from Settings, generate an encryption key and paste it as `AI_CREDENTIAL_ENCRYPTION_KEY`:

   ```powershell
   python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
   ```

   The key is only needed if you use a cloud provider. Keep the same key when restarting or rebuilding. If it is lost, previously saved cloud keys cannot be decrypted.

4. Start the project:

   ```powershell
   .\scripts\start-docker.ps1
   ```

   Open the frontend URL printed by the script (normally `http://localhost:8080`). Create an account. The API is normally at `http://localhost:8000`; `/api/v1/health` reports API/database health.

## Settings and AI providers

Open **Settings → AI Models**. Choose OpenRouter, Groq, Google Gemini, xAI/Grok, OpenAI, Cerebras, Together AI, or OpenAI-Compatible Custom Provider. Enter the API key for cloud providers, use **Fetch Models**, select a model, then **Test Connection** and save. The key field is masked and saved keys are encrypted by the API; they are never returned to the browser. On chat, your request, recent relevant conversation turns, and matching limited workspace context are sent to the provider you chose. Low Token Usage limits context and response size. Free-model pricing is shown only when a provider returns pricing metadata, and quotas/availability can change.

## Logs, restart, rebuild, stop

All commands below target only this project:

```powershell
docker compose -p dayweave-ai ps
docker compose -p dayweave-ai logs -f backend
docker compose -p dayweave-ai logs -f postgres
docker compose -p dayweave-ai restart
docker compose -p dayweave-ai up -d --build
docker compose -p dayweave-ai down
```

`down` preserves the database and uploaded-file volumes. Do not add `-v` if you need that data. If a port is occupied, change `BACKEND_PORT` or `FRONTEND_PORT` in `.env`, then run the rebuild command.

## Database backup and migration

Compose runs the Alembic migration before the API starts. To migrate manually:

```powershell
docker compose -p dayweave-ai exec backend alembic upgrade head
```

To create a SQL backup in the project folder:

```powershell
docker compose -p dayweave-ai exec -T postgres pg_dump -U dayweave -d dayweave > .\dayweave-backup.sql
```

Restore only after checking the backup and target database. Restoring to a non-empty database can fail on duplicate records; do not use a destructive reset command on a database containing data.

## Troubleshooting

- **Docker engine access denied or pipe unavailable:** open Docker Desktop, wait for its engine to start, then retry. No containers need to be removed to fix a stopped engine.
- **Frontend/API port conflict:** set unused host ports in `.env`; the start script also checks for free ports.
- **Database health check fails:** inspect `docker compose -p dayweave-ai logs postgres` and confirm `.env` has the same database name/user/password on each restart.
- **Saved cloud key cannot decrypt:** restore the same `AI_CREDENTIAL_ENCRYPTION_KEY` used when it was saved, or replace the API key in Settings.

## Render

Render uses `render.yaml`, not this Compose stack. Create a Blueprint from the repository, provide a new `AI_CREDENTIAL_ENCRYPTION_KEY` when prompted, and use the PostgreSQL connection generated by the Blueprint. Configure a paid persistent PostgreSQL plan before relying on it for real user data; Render's free database expires. Configure a cloud provider from the Settings page after deployment. Keep the encryption key stable across deploys and backups.

This repository's Render configuration and database migration can be prepared locally, but deployment and PostgreSQL runtime behavior must be verified in the Render environment.
